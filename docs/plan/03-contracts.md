# Data, API, and behavior contracts

This document fixes semantics before local models write code. T01/T02 turn these tables into exact SQL/SDL and executable fixtures; those accepted artifacts become authoritative. An implementer may not invent a competing meaning. Proposed changes require an ADR and affected contract/test updates before resuming dependent tasks.

## Shared value rules

- UUID IDs are opaque strings; never authorize based on unpredictability. Revision is positive integer. Unknown values are null, not magic strings or zero.
- DateTime: RFC3339 UTC instant. LocalDate: strict Gregorian YYYY-MM-DD. Timezone: validated IANA identifier. Date-only acquisition never silently becomes an instant.
- Decimal: canonical decimal string (no exponent, max 6 fractional digits), exact DB numeric. Money: nonnegative minorUnits as digit string and ISO currency code with validated currency exponent. No JS/Go floating-point money. Negative refund adjustments use explicit credit entries, not negative purchases in v1; credits deferred, UI explains this limit. Initial currency chosen by owner; multi-currency records allowed but totals grouped by currency, never converted implicitly.
- Measurements carry quantityKind and compatible unit; normalize for comparisons while retaining original input. Water mL/L, fertilizer g/mL with concentration/product reference optional, height mm/cm, harvest g/kg/count, temperature C/F. Water and fertilizer cannot share one untyped numeric field.
- All user-visible records have createdAt/updatedAt; event time is separate. Text limits: names 160 characters, notes 20,000, tag 40, search 200. Server validates; UI mirrors.

Acquisition provenance is authoritative for plant source/date; plants.acquiredOn is a read projection updated in the same transaction, never edited independently. All monetary purchase records represent known amounts (including zero); unknown costs belong to acquisitions, not null/zero purchase totals.

Plant archive/death preserves journal/photos/purchases; future occurrences cancelled and new automatic analyses disabled. Explicit restore can regenerate future occurrences without recreating completed work. Permanent purge is a separate authenticated operation requiring typed confirmation; removes plant-owned data and dependent AI snapshots, preserves shared purchase record with allocation label replaced by deleted-plant marker. Purge rebalances nothing and cannot change historical totals. Files referenced elsewhere survive; unreferenced assets collected after 7-day grace. Backups expire by operator policy and are disclosed in deletion UI.

## Purchases: exact arithmetic

Purchase $100.00 including $5 tax and $5 shipping; two $45 line subtotals. Allocate each line to a different fig. Each fig shows $50.00 total. The purchase remains one $100.00 expense, not $200.00 because the receipt is linked twice.

Owner can assign overhead manually, or server distributes proportionally by allocated subtotal with largest-remainder rounding and stable allocation ID tie-break. All-zero subtotal requires explicit overhead allocation. Unallocated supplies appear in workspace total but not individual plant totals. Editing uses expectedRevision and one transaction; allocations cannot exceed/subceed any line or overhead component. Spending queries exclude voided purchases and group currency. Unknown purchase costs are separate count, never silently summed as zero. Receipt OCR only proposes draft lines; owner confirms reconciliation.

### Acquisition pricing and transitions

`recordAcquisition` records source/date with pricingState UNKNOWN and no purchase allocation, or KNOWN with an existing allocation to that plant. It can atomically create the priced purchase/line/allocation when a price is supplied. `updateAcquisition` changes provenance using expectedRevision. `priceAcquisition` transitions UNKNOWN to KNOWN by linking an existing allocation or atomically creating a new known purchase; same acquisition ID and one journal acquisition entry remain. Linking a shared purchase prices several acquisitions without making duplicate purchase records. Reverting KNOWN to UNKNOWN detaches the acquisition link without voiding the financial purchase; UI explicitly distinguishes acquisition price from remaining plant-attributed spending. Voiding a linked purchase atomically marks affected acquisition pricing UNKNOWN, retains provenance and audit.

Spending reports contain `knownSpendingByCurrency`, `unknownAcquisitionCostCount`, and `missingAcquisitionRecordCount` separately. Known free acquisition requires a zero-total purchase/allocation and displays Free; UNKNOWN displays Price unknown; no acquisition record displays Acquisition not recorded. Plant lifetime spending includes all known allocated purchases, even if initial acquisition cost is unknown. Per-plant acquisition-price query reads its linked allocation only, not total lifetime spending. Purchase edits preserve allocation IDs for allocations that remain on the same plant. Removing or reassigning an acquisition-linked allocation is rejected unless the command explicitly includes that acquisition ID in `unlinkAcquisitionIds` after a UI confirmation; with that opt-in, the transaction marks it UNKNOWN and increments its revision before changing the allocation. Recreating a line cannot silently delete a referenced allocation (FK RESTRICT). Changes to amounts on a retained allocation update the derived acquisition price and invalidate dependent analysis snapshots. Cross-record checks run in a transaction locking purchases first and acquisitions second, each in stable UUID order; revision increments and unique constraints prevent concurrent double linkage.

Required fixture set: (1) lemon acquired from nursery, price unknown, count=1 unknown; (2) gifted lime with known free purchase, known total=0, unknown count=0; (3) mandarin with no acquisition record, missing count=1; (4) two unknown fig acquisitions later linked to one $100 purchase with $50 allocations each, same acquisition IDs and exactly one workspace expense. Decimal zero is never used for missing information.

### Permanent purge and retained-copy matrix

Purge is stronger than archive; confirmation states precisely what remains (shared financial documents/totals, minimal security/deletion tombstones, expiring backups and data already delivered externally). It does not promise to retract emails or erase provider-held data. External provider retention policy is disclosed before opt-in; provider deletion requests are best effort where supported and status visible.

A workspace privacy epoch increments on purge. Transaction locks target aggregate, records minimal deletion tombstone, removes/redacts canonical and copied live data, invalidates applicable mutation responses, cancels/fences jobs, and revokes exports. All async/export commits compare epoch and target generations before publishing. A privacy-barrier test covers mutation replay, reads and in-flight jobs; SQL transaction isolation/locking prevents reads begun after the purge commit from observing retained copies. Requests already in flight cannot be retracted; caches require revalidation on epoch change.

| Data class | Purge behavior and deadline |
|---|---|
| Plant, contexts, acquisition, tags links, activities, measurements, photo links, journal projection | Remove target records transactionally; preserve no free-text copy. Minimal tombstone stores opaque deleted ID, timestamp/action/actor only. |
| Shared purchases and allocations | Preserve financial totals/seller/date and shared receipts. Replace plant relation/display name by deleted-plant marker; redact plant-specific line descriptions where possible without changing amounts. Confirmation explicitly says documents may still contain plant text; owner can separately remove receipt if desired. |
| Audit prior/current values | Redact target content, photo metadata and copied summaries in same transaction; retain actor/action/time/opaque ID/revision only. Audit cannot bypass erasure policy. |
| Idempotency responses | Maintain reverse entity-reference index for stored responses. Replace responses touching purged IDs with minimal `RESOURCE_GONE` tombstone in same transaction; preserve operation/key/input hash until original 30-day TTL. Same-key replay never recreates or returns deleted entity, regardless of original response. Purge command itself replays minimal success. |
| Analysis snapshots/results, suggestions, guidance copies | Delete target snapshots/results and redact evidence references from multi-plant results; invalidate whole multi-plant result if safe redaction cannot preserve meaning. No raw prompts/results in logs. |
| Notification bodies and pending delivery | Redact/delete target content and cancel pending delivery. Already delivered external email cannot be withdrawn; minimal delivery status may remain. |
| Export files/jobs | Revoke ALL workspace exports immediately via epoch; authenticated download fails before unlink. Delete encrypted/unencrypted generated archive files within 24h, cancel in-progress exports and discard old-epoch results. Owner-downloaded copies cannot be erased remotely. |
| Queued/running jobs and stored results | Cancel/fence by epoch/generation; River payloads contain opaque IDs only. Delete result copies; late provider/media/job completion discards output. Infrastructure job IDs/status may remain to normal job retention. |
| Original/derived files | Unreferenced target assets hidden immediately, physically removed within 7 days including temp files. Shared receipt assets retained until last authorized link removed. Photos cannot share with other plants implicitly. |
| Application caches/logs | No private content in logs; clear server cached target values immediately. Epoch-aware UI invalidates on next request; private media uses revalidation and no persistent browser cache for originals. No v1 service worker. |
| Backups | Already-created encrypted backup retains data until disclosed 7-daily/4-weekly expiry. Maintain a separate encrypted deletion ledger outside historical archives, alongside the current backup-set watermark; purge reports pending until this ledger is durably replicated to configured backup destination. Restore refuses unattended access without the latest operator-verified ledger/watermark; restore re-applies purge tombstones/epoch before reopening access so old backups cannot silently resurrect deleted content. This ledger itself has no erased free text. |

Unlink and archival jobs use idempotent retries; deletion errors surface to owner with pending-erasure status. Tests inspect DB/files/exports/replay records for surviving copied strings, not merely absence from UI. Purge-vs-export/analysis concurrency and shared receipt survival are mandatory PORTABILITY cases.

## HTTP and upload protocol

- `POST /api/auth/login`, `GET /api/auth/session`, `POST /api/auth/logout`; login validates exact Origin and JSON-only content; session returns CSRF token after auth. Rate-limited. Password change via authenticated HTTP endpoint with old password and CSRF; no GraphQL exposure of secrets.
- `PUT /api/uploads/{assetID}` streams bytes after reserveUpload; requires session/CSRF and one short-lived reservation. No file bytes through GraphQL. Maximum image 25 MiB, receipt 20 MiB, 80 megapixel decode bound, per-workspace default quota 10 GiB adjustable by operator. Claimed and received sizes must match. Allowed image input JPEG/PNG/WebP/HEIC/HEIF; receipts PDF or those images. MIME sniffing and decode validity override extension.
- Upload to opaque temp file, checksum, fsync, atomic rename on same filesystem. One successful stream per reservation; identical repeated checksum returns existing success; different content returns conflict. Empty/oversized/truncated input fails cleanly. Expire unused reservations in 24h. A file before DB commit is an orphan candidate; DB PROCESSING without file is recoverable failure. Sweeper reconciles both.
- finalizeUpload checks bytes/hash and transactionally marks/enqueues processing. Repeat is safe. Receipt PDFs checked by signature/size and downloaded as attachment only; images normalized in restricted worker subprocess, no embedded HTML/SVG permitted.
- Worker emits deterministic derivative keys per asset+processorVersion. Original remains private. Display copies have orientation fixed and GPS metadata stripped. Photo takenAt uses explicit owner value first, EXIF timestamp plus known offset second; naive EXIF prompts for timezone, fallback is visibly upload time. No silent date invention.
- `GET /api/media/{assetID}/{variant}` authenticates owner, enforces READY and purpose, fixed variants, safe Content-Type and Content-Disposition, `nosniff`, private revalidation (`Cache-Control: private, no-cache`) and ETag; epoch change revokes stale media authorization. Never accepts a storage path. Unauthorized and absent both 404. Private originals/downloads not cached by service worker; service worker absent in v1.
- Deletion transaction hides links immediately and creates cleanup job; actual delete waits for reference check/grace. Worker rechecks target state before committing results. Images/photos/purchases cannot link assets in other workspaces.

## Scheduling contract

Care engine is a pure function of profile version + context + user overrides + event history + weather snapshot + clock. Output contains checks, reasons, missing inputs, validity. Scheduler and notifications are adapters around it.

Supported recurrence (not arbitrary RRULE): (a) every N local calendar days anchored to start or last qualifying completion; (b) selected weekdays; (c) annual local month/day windows with cadence; (d) one-time local date. Profile rules explicitly choose anchor policy. N 1–365, schedule horizon 60 days; dates beyond horizon generated on future ticks. Feb 29 maps to Feb 28 in non-leap years, recorded in reason. Windows spanning New Year and southern-hemisphere seasons use explicit dates/region, never month inversion guesses.

Tasks due as local dates, shown in workspace timezone with original plan timezone available. Notification time default 09:00 in plan timezone; DST nonexistent time moves to next valid instant; ambiguous time uses earlier offset; unique occurrence/date/channel prevents double sending. A fixed occurrence's logical key never changes with snooze. For completion-relative intervals, materialize only next actionable occurrence; completing (including backdated completion) recalculates future uncompleted occurrence, preserves completed/skipped history. Seasonal/weekday plans maintain scheduled cadence; completion never shifts it. Skip advances one cycle without activity; snooze changes effective due date but not cadence. Completing overdue recurring check creates one activity and one next occurrence, not a burst for every missed day.

### Completion-relative cursor and skip examples

Store a rule-level recurrence cursor (last resolved occurrence ordinal, decision kind, anchorDate, nextDueDate) independently from activity history. For interval N: completing the current actionable occurrence anchors nextDueDate to actual completion local date + N; skipping anchors nextDueDate to that occurrence's original scheduled due date + N (not click date or snoozed date). Repeated skips each advance one original cycle. At most one actionable completion-relative occurrence exists. Historical resolved occurrence due dates are immutable; correcting an earlier completion does not rewrite a later skip/completion decision. Latest resolved decision determines cursor; corrections to the latest completion may recalculate only current uncompleted work. Undo after any later resolved decision retracts history without reopening the old occurrence.

Dated N=7 examples: Jan 1 due → skip → Jan 8 due → skip → Jan 15 due. Complete Jan 15 occurrence on Jan 17 → Jan 24 next due; complete it with explicit backdate Jan 14 → Jan 21 next due. Separately, complete Jan 1 occurrence Jan 2 → Jan 9 due, skip Jan 9 → Jan 16 due, then correct earlier completion from Jan 2 to Jan 3: Jan 9 skip remains immutable and Jan 16 stays next. Snoozing Jan 9 to Jan 12 then skipping still advances to Jan 16. Each scenario asserts exact cursor/next date, preserved skipped history and unique logical key.

### Correcting a completed occurrence

A linked completion activity is not edited/voided through the general activity command; that command returns `LINKED_COMPLETION_USE_CORRECTION` with occurrence ID. `correctOccurrenceCompletion` handles note/quantity/time correction or undo atomically with activity revision, occurrence state/history, timeline, future materialization and notification intents. Editing note/quantity leaves cadence unchanged. Editing occurredAt recalculates completion-relative next work; scheduled-calendar cadence remains fixed.

Undo voids the linked activity, appends audit and clears completion link. If no later occurrence on the same rule was resolved (COMPLETED or SKIPPED), reopen the occurrence as one overdue check and cancel/recompute future uncompleted completion-relative work; calendar plans retain cadence. If a later occurrence was already resolved by completion or skip, never reopen or shift newer history: mark the older occurrence `COMPLETION_RETRACTED` (add enum state), leave that later scheduling decision and its derived cadence authoritative, and show corrected history. Notifications already sent are not retracted; cancel unsent intents for invalidated future occurrences and schedule next digest using stable unique keys. Concurrent undo/complete is protected by rule+occurrence row locks/revisions. Browser preview explains which dates will change before confirmation. Required tests cover undo before next completion, undo after next completion, timestamp correction across local date/DST and duplicate correction replay.

Tick every 5 minutes, plus startup catch-up from persisted scheduler cursor. Application uniqueness keys make duplicate ticks harmless. Backlog collapses repeating missed daily checks to one overdue actionable check per rule, not hundreds of notifications; fixed one-time events stay distinct. Daily digest delivery default, optional immediate notification for accepted severe weather checks; no repeat digest for identical occurrence unless due status changes or next local day, and never more than one digest/day. On plan edit cancel only future uncompleted affected occurrences; preserve history and transactionally regenerate. Timezone changes require explicit recalculate preview.

Weather is advisory: fresh <= 6h, stale <= 24h shown as stale, older treated unavailable. Covered/indoor contexts ignore rainfall for water guidance. Temperature/rain can elevate “check soil/protect from frost”, never mark watered, skip fertilizer automatically, or assert soil moisture. Container and ground profiles differ. Freeze thresholds, fertilizer timing, harvest windows, and pruning rules require reviewed region/cultivar sources. Each rule fails closed to “needs context” for missing required facts.

## AI, identification, and OCR

Runtime provider ports: TextAnalyzer, VisionAnalyzer, PlantIdentifier, ReceiptExtractor. Coding model Strata is a separate tool, not automatic runtime vision capability. Providers expose capabilities at startup and have explicit owner opt-in for sending private photos/receipts externally. Endpoint/key operator-owned; settings expose capability/status/model name without credentials.

Analysis run flow: QUEUED → RUNNING → SUCCEEDED / FAILED / CANCELLED / STALE. Domain operation inserts run + River job transactionally. Claim run with attempt/generation; call provider outside transaction; commit only if generation and snapshot still valid. A deleted/modified target or cancelled run makes result stale/discarded; late provider response cannot resurrect data. Retry only timeout/429/5xx up to 3 attempts, bounded exponential jitter; schema failure allows one bounded repair then fails. Validate JSON length/schema/enums/evidence refs before persistence; no raw unvalidated output rendered.

Input snapshot includes selected plant/context revisions, source versions, activity/measurement/photo IDs and hashes, weather freshness, prior relevant observations, and missing facts. Bounded selection: latest 12 relevant activities, at most 4 image derivatives, retrieved approved guidance, maximum provider-specific token budget; user sees what was included. Full snapshot/hash stored for reproducibility with private retention controls; structured results separate from untrusted raw provider data.

Result schema: visibleObservations[], hypotheses[] with confidence LOW/MEDIUM/HIGH and evidence IDs, missingInformation[], followUpChecks[], suggestedTasks[], citations[]. Cross-record text insights can reference purchase cost changes and care history without asserting causation. Confidence is a model label, not calibrated probability. Engine validates citations reference supplied sources and entity IDs; unsupported claims flagged and cannot become actionable care automatically. Documents/receipt text/photos are untrusted data, never instructions; model has no tools, arbitrary URLs, SQL, or secrets. No automatic training on owner data.

Budget: default 10 analysis runs/day/workspace, max one concurrent run/provider, configurable 5 USD/month external cost ceiling where prices known. Budget ledger uses integer micro-USD internally (not binary floats) and UTC calendar-month boundaries. Each potentially billable provider attempt, including retry or schema-repair request, atomically reserves its own maximum input/output cost BEFORE dispatch; no remaining budget means no dispatch. Initial enqueue reserves first attempt. Require operator-defined USD price bounds or explicit bounded per-run approval if price unknown. A timeout/disconnect/cancel after dispatch may still be charged: keep worst-case amount encumbered until authoritative usage/invoice reconciliation; never auto-refund merely because output failed, was cancelled or discarded. Refund only undispatched attempts or proven unused amount. All attempts/repair count against provider request/token ceilings. An attempt belongs to UTC month of dispatch; outstanding prior-month reservations cannot migrate into new-month allowance, and late final usage reconciles against its original ledger. Concurrency locks budget rows and dispatch IDs; maximum possible known plus encumbered spend cannot exceed configured ceiling. Tests cover timeout-after-charge, retry+repair, cancellation-after-dispatch, unknown usage and simultaneous month-boundary requests. Local provider uses run/token/time ceilings even without monetary charge. No repeat analyses without new input hash unless owner explicitly reruns. Provider failure never affects journal writes.

OCR creates editable receipt draft, preserves original, never writes confirmed purchase. Identification shows ranked candidates and confidence; owner accepts scientific name; cultivar stays unconfirmed unless label evidence. Vision summarizes visible change, not growth rate without scale/reference or definitive disease. Suggested tasks need owner acceptance plus deterministic profile/context validation. Initial assistance is asynchronous with polling while detail is visible (2s active, exponential to 15s; stop on terminal state/route leave), no subscriptions/WebSockets required.


## AUTH01 approved extension — users and browser setup

The original CLI-only single-owner authentication constraint is superseded by browser first-run setup and administrator-managed users. The garden owner/workspace IDs remain data-scoping identities; a separate user identity records the human session. All members share that garden with normal editing rights; Administrators additionally manage users, sign-in connections, AI credentials and agent credentials. Existing owners are migrated to username `owner` with their original password. Legacy password-only login and CLI owner recovery remain supported for the primary account.

Authentication stays on `/api/auth/*`, outside the business GraphQL schema. `GET /api/auth/options` returns setup availability and the enabled SSO display name. `POST /api/auth/setup` atomically initializes an empty instance; later calls conflict. Login accepts username/password and session responses additionally expose sanitized current-user metadata. Authenticated `/api/auth/me`, `/users`, and `/oidc/settings` expose profile, admin user CRUD and generic OIDC settings. Writes require the existing Origin/CSRF protections. OIDC start/link/callback use short-lived server-side one-time state with an HttpOnly browser binding; no access/ID token reaches the browser application. Linking is explicit to the authenticated account; issuer+subject are identity keys and email never grants access. Optional OIDC auto-enrollment creates Members only. No further public password signup is available after setup.
