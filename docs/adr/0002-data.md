# ADR-0002: R1 data model and persistence decisions

Date: 2026-11-01
Status: Accepted
Deciders: implementer (T02.r1), owner directive to proceed

## Context

R1 needs a relational model that enforces the semantics frozen in
`docs/plan/03-contracts.md` and the GraphQL SDL in `contracts/graphql/`:
workspace scoping, exact decimal/money semantics, optimistic concurrency,
idempotent mutations, a unified journal timeline, acquisition provenance
with purchase pricing, and media lifecycle. Care/AI tables are deliberately
out of scope (T02.care/T02.ai land as later migrations).

## Decisions

1. **PostgreSQL 17 is the only source of truth.** UUID PKs generated
   application-side; every scoped table carries `workspace_id`; all
   cross-record links are workspace-scoped FKs. Dev/test DB is a disposable
   `postgres:17` container (digest pinned in ADR-0001 §9).

2. **Native Postgres enums** for closed sets (plant status/type/category,
   activity kind, quantity kind, units, asset state, etc.). DB CHECK is
   free; sqlc generates typed Go constants. Adding a value is
   `ALTER TYPE ... ADD VALUE` — acceptable migration cost for R1 stability.

3. **Money is exact**: `numeric` minor-unit columns, never float.
   `CHECK (tax_minor + shipping_minor <= total_minor)` and nonnegativity at
   DB level. Negative refunds are out of scope for R1 (explicit credit
   entries deferred).

4. **Measurement/activity unit compatibility is a DB CHECK**:
   `VOLUME→ML|L`, `MASS→G|KG`, `LENGTH→MM|CM`, `COUNT→COUNT`,
   `TEMPERATURE→C|F`; water requires volume units, fertilizer mass-or-volume,
   other kinds carry no quantity. `quantity IS NULL ⟺ unit IS NULL`.
   Verified by constraint tests, not assumed.

5. **Optimistic concurrency**: every mutable aggregate has `revision`;
   updates are `UPDATE ... WHERE id=$1 AND workspace_id=$2 AND
   revision=$expected RETURNING` — zero rows means CONFLICT. Prior values go
   to `audit_revisions` in the same transaction.

6. **Idempotency**: `mutation_receipts` unique on
   `(workspace_id, operation, idempotency_key)`; insert is
   `ON CONFLICT DO NOTHING RETURNING` — no row means replay: compare
   `request_hash` to decide replay vs `IDEMPOTENCY_CONFLICT`.

7. **Journal is a projection table** (`journal_entries`), written in the same
   transaction as the source record. Unique
   `(workspace_id, entry_type, source_id, plant_id)` makes projection
   idempotent (`UpsertJournalEntry` re-projects on source edit). Deletes
   tombstone (`tombstoned_at`) so history stays honest. Timeline reads are a
   single index scan on `(workspace_id, plant_id, occurred_at DESC, id DESC)`.

8. **Acquisition ↔ allocation circularity**: `acquisitions.initial_purchase_allocation_id`
   references `purchase_allocations` with `DEFERRABLE INITIALLY DEFERRED` so
   createPlant + purchase + line + allocation + acquisition commit in one
   transaction regardless of insert order. `pricing_state='KNOWN' ⟺
   allocation present` is a DB CHECK; one acquisition row per plant
   (`UNIQUE (workspace_id, plant_id)`).

9. **`plants.acquired_on` is a read projection** of the acquisition record,
   updated only in the same transaction; never independently editable.

10. **Plant contexts are immutable**: no UPDATE path; every placement/location
    transition inserts a new row effective from a timestamp. History is
    reconstructable without audit queries.

11. **Partial unique indexes** encode R1 cardinality rules: one live cover
    photo per plant (`WHERE is_cover AND deleted_at IS NULL`), one live tag
    per normalized label per workspace (`WHERE archived_at IS NULL`) —
    archiving frees the label for a new tag while old links keep pointing at
    the archived row.

12. **Keyset pagination everywhere**: row-value comparisons
    `(sort_key, id) > (cursor_key, cursor_id)`; cursors are opaque
    (base64 of filter signature + key fields). No OFFSET.

13. **`updated_at` via trigger** (`set_updated_at()`), not app discipline.

14. **Purge fencing**: `workspace.privacy_epoch` bigint bumped inside the
    purge transaction; async jobs and export commits compare it and abort on
    mismatch.

15. **sqlc v1.31.1 + pgx/v5** with committed generated code
    (`server/db/generated`, package `dbgen`). Generation is byte-reproducible
    (sha256 of generated tree identical across runs). Numeric columns map to
    `pgtype.Numeric` (pointer for nullable).

16. **Migrations are goose-format** (`server/db/migrations/00001_r1_core.sql`,
    `-- +goose Up/Down`). The goose runner ships in T04 `cmd/migrate`;
    the acceptance suite applies the Up section directly per-test-schema.

## Implementation notes (learned during T02.r1)

- sqlc v1.31 cannot resolve window-function columns through CTEs/subqueries;
  the bounded per-plant selection uses `unnest(...) CROSS JOIN LATERAL
  (… LIMIT n)` instead — which also produces a better plan (per-plant index
  scans).
- Nullable boolean filter args must be `COALESCE(narg, false)` in predicates,
  or a NULL parameter silently turns `NULL OR x` into NULL and drops rows.
- sqlc names parameters from the nearest expression (`lower($2)` → `Lower`);
  use `sqlc.arg('name')` where the API name matters.

## Validation evidence (see .artifacts/agents/T02/)

- 21 constraint/behavior tests pass against real postgres:17
  (`server/db/db_test.go`, isolated schema per test): unit compatibility,
  money checks, pricing-state invariants, deferred-FK one-transaction
  creation, cover/tag/journal uniqueness, revision guard, idempotency
  receipts, text limits, bounded per-plant activity fetch, voided-purchase
  exclusion.
- EXPLAIN (ANALYZE, BUFFERS) on a seeded dataset (2k plants, 50k journal
  entries, 20k activities, 5k purchases): journal first page 0.45 ms,
  plant-scoped deep page 0.33 ms, plants keyset+search 0.14 ms,
  25-plant×12-activity fetch 0.48 ms — all index scans.
- Known scale notes: workspace-wide spending aggregates seq-scan purchases
  (2.6 ms @ 5k rows) — add a covering index when row counts warrant;
  `ILIKE '%…%'` search will need `pg_trgm` at larger plant counts.

## Consequences

- Cross-row arithmetic invariants (allocation sums vs line totals, overhead
  splits) cannot be single-column CHECKs; they are enforced atomically in
  the service transaction that writes both rows — T08 resolvers must keep
  them in one transaction.
- Committed generated code means migrations/queries changes show up as
  reviewable diffs; CI regenerates and fails on drift (T03).

## Addendum: care schema (T02.care)

- Migration numbering is reserved by lane: `00001` R1 core, `00002`
  portability (T38.a), `00003` care (T02.care), `00004` AI (T02.ai, landed
  out-of-order — see the AI addendum). Additive-only; never rewrite an
  accepted migration.
- Recurrence is stored as a `jsonb` object discriminated by `"form"`, not an
  RRULE string — the four frozen forms are closed and engine-native:
  - `{"form":"EVERY_N_DAYS","days":1..365,"anchor":"PLAN_START"|"LAST_QUALIFYING_COMPLETION"}`
  - `{"form":"WEEKLY_DAYS","weekdays":["MONDAY",...]}` (1–7 entries)
  - `{"form":"ANNUAL_WINDOW","month":1..12,"day":1..31,"window_days"?:1..366,"every_years"?:1..50}`
  - `{"form":"ONE_TIME","date":"YYYY-MM-DD"}`
  The DB enforces form + numeric ranges via `valid_recurrence(jsonb)`; enum
  membership (weekday names) and calendar semantics are validated by the care
  engine (T22). `valid_recurrence` wraps its CASE in `COALESCE(..., false)`:
  a NULL branch result would make the CHECK pass (CHECKs accept NULL).
- Immutability is trigger-enforced, not service-honor-system:
  `source_versions` rejects all UPDATEs; `care_profile_versions` allows
  DRAFT edits, DRAFT→REVIEWED publish (reviewer fields required in the same
  UPDATE), REVIEWED→RETIRED (status + `retired_at` only), and rejects DELETE
  for non-DRAFT rows; `care_rules` are writable only while their version is
  DRAFT. Publish therefore inserts the new version as DRAFT, copies rules,
  then flips it to REVIEWED in one transaction.
- `journal_entry_type` gains `CARE` via `ALTER TYPE ... ADD VALUE` (PG12+
  in-transaction legal, value unreferenced inside the migration). Enum values
  are never removed; the Down section drops relations only. The GraphQL union
  member (`extend union JournalEntry = CareEntry`) is wired at T24 together
  with server support.
- Occurrence identity: `UNIQUE (plan_id, occurrence_key)` — the logical key
  never changes across snooze/regeneration; `current_due_date >=
  original_due_date` and `snoozed_until >= current_due_date` encode the
  forward-only rules. Agenda reads use the partial index on `(workspace_id,
  current_due_date, id) WHERE status = 'DUE'`.
- Notification dedup: `UNIQUE (workspace_id, dedup_key)` makes duplicate
  scheduler ticks idempotent at the storage layer.

## Addendum: AI schema (T02.ai)

- `00004_ai_analysis.sql` backfills **out-of-order**: it landed after
  `00005`–`00007` were already applied on long-lived databases. Goose halts
  on gaps by default, so `server/cmd/migrate` now builds the goose provider
  with `WithAllowOutofOrder(true)`: out-of-order migrations are applied in
  numeric order relative to each other, before genuinely new ones. Proven on
  a scratch DB staged at 00001–00003 + 00005–00007 (evidence
  `.artifacts/agents/T02/`).
- New PG enums: `analysis_kind`, `analysis_run_state`, `analysis_failure_code`,
  `suggestion_kind`, `suggestion_severity`, `suggestion_status`.
  `journal_entry_type` gains `INSIGHT` via `ALTER TYPE ... ADD VALUE` (CARE
  pattern); the GraphQL union member is wired at T33 with server support.
- `analysis_runs`: `capability` is a CHECK-constrained text (closed list,
  not an enum, so adding a capability is a CHECK swap, not an enum migration).
  Target shape per kind is a DB invariant: `chk_run_target_by_kind` (receipt
  extraction ⇒ receipt asset only; vision ⇒ plant + distinct photo pair; text
  ⇒ plant) and `chk_run_photo_pair_distinct`. State timeline,
  success-requires-result, and failure-requires-code are CHECKs.
- Worker fencing: every state transition carries the row's `generation`;
  claim bumps it, so a superseded worker's commit/fail matches zero rows
  instead of clobbering. `attempts` is bounded 0..3 at the claim guard.
  Cancel/accept/dismiss use a `revision` guard (optimistic concurrency).
- Semantic-key dedup is **active-only**: partial unique
  `analysis_runs_active_semantic_uk ON (workspace_id, semantic_key) WHERE
  state IN ('QUEUED','RUNNING')` — a terminal run frees its key, so reruns
  are new rows, never in-place resets.
- Cost accounting is micro-USD bigint. Reservation is encumbered at insert
  and survives cancellation; `cost_actual_micro_usd` NULL means *unknown*,
  settled exactly once after terminal state. `BudgetMonthTotals` returns
  `actual_count` alongside the sums: count 0 ⇒ callers report NULL, never 0
  (sqlc 1.31.1 infers aggregates non-null and has no comment override, so the
  distinction is carried in data, not type inference).
- `suggestions`: `(status='ACCEPTED') = (accepted_task_id IS NOT NULL)` is a
  CHECK, and `accepted_task_id` FKs to `care_occurrences` — accepting advice
  creates exactly one task, once. `needs_review` + revision guard make
  in-flight accepts of invalidated advice fail (CONFLICT) until an explicit
  owner review touch. Expiry must be future at write time (CHECK on INSERT
  and UPDATE); the sweeper flips only `PROPOSED` rows. `evidence_ids`/
  `missing_facts` are NOT NULL jsonb arrays, `COALESCE`d to `'[]'` in
  `InsertSuggestion` because Go callers omit them as NULL.
- Cross-workspace consistency stays service-level (as everywhere else in the
  schema — no composite FKs exist): every query is workspace-scoped, and
  target refs (plant/receipt/photos/task) are validated in the service
  transaction that writes the row.
- Index evidence at 50k rows/50k suggestions (`.artifacts/agents/T02/
  explain-scale.txt`): keyset paging walks the workspace/plant recency
  indexes sub-ms, semantic-key lookup hits the partial unique, 7-day run
  counts hit the month index; the expiry sweep seq-scans only because the
  staged fixture leaves 76% of rows pending — the partial index serves the
  realistic small-pending steady state.
